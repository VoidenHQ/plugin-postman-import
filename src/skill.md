## Extension: Postman Collection Importer

This extension also ships a one-click **Import into Voiden** button (for an opened Postman v2.1 export) that always produces one `.void` file per request, folders mirrored as directories. **This skill is not about that button's output** — it teaches an agent how to **generate `.void` files directly from a Postman collection's raw JSON**, e.g. when asked to "convert this Postman collection into Voiden requests." Read `voiden-rest-api`'s skill alongside this one for full block syntax (`request`, `headers-table`, `query-table`, `path-table`, body blocks), `voiden-advanced-auth`'s skill for the `auth` block, and `voiden-graphql`'s skill for `gqlquery`/`gqlvariables`.

### Default generation strategy: one file per resource, not per request

A Postman collection's `item` array is a tree of folders (`{name, item: [...]}`) and requests (`{name, request, event}`). Don't default to one `.void` file per request. Instead: **for a folder whose child requests operate on the same resource (the common shape: `Create X` / `Get X` / `List X` / `Update X` / `Delete X`, or any folder of related leaf requests), generate ONE `.void` file for that folder**, with each child request becoming its own section via a `request-separator` (base skill's Multi-Request Files feature), not a separate file. Only fall back to one file per request when a request stands alone with no siblings worth grouping.

```markdown
---
version: __VOIDEN_APP_VERSION__
generatedBy: Voiden app
note: This file is auto-generated by the Voiden app
generatedAt: 2025-01-15T10:30:00.000Z
---

# User CRUD

```void
---
type: request-separator
attrs:
  uid: "c3d4e5f6-a7b8-4c9d-e0f1-a2b3c4d5e6f7"
  colorIndex: 0
  label: "Create User"
---
```

```void
---
type: request
attrs:
  uid: "a1b2c3d4-e5f6-4789-ab01-cd23ef456789"
  content:
    - type: method
      attrs: { uid: "...", method: POST, visible: true }
      content: POST
    - type: url
      attrs: { uid: "..." }
      content: "{{BASE_URL}}/users"
---
```

```void
---
type: json_body
attrs:
  uid: "..."
  body: |
    { "name": "Alice", "email": "alice@example.com" }
---
```

```void
---
type: runtime-variables
attrs:
  uid: "..."
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [user_id, "{{$res.body.id}}", "Captures the new user's id for the sections below"]
---
```

```void
---
type: request-separator
attrs:
  uid: "f6a7b8c9-d0e1-4f2a-b3c4-d5e6f7a8b9c0"
  colorIndex: 1
  label: "Get User"
---
```

```void
---
type: request
attrs:
  uid: "..."
  content:
    - type: method
      attrs: { uid: "...", method: GET, visible: true }
      content: GET
    - type: url
      attrs: { uid: "..." }
      content: "{{BASE_URL}}/users/{{process.user_id}}"
---
```
```

Keep going with the same pattern for `Update User` (PUT/PATCH) and `Delete User` (DELETE) sections. Section `label`s name the operation — don't add a redundant `## Create User` heading (see "Placement" below).

**Chaining sections together:** a section's response can feed the ones after it via a `runtime-variables` block (shown above) or a `post_script` calling `voiden.variables.set()`. Referencing a captured value always requires the `process.` prefix — `{{process.user_id}}`, never `{{user_id}}` — see the base skill's "runtime-variables" section for the full capture-expression table (`$res.body.path`, `$res.headers.name`, `$req.url`, etc.). A Postman request's own `event[].script.exec` (see mapping below) is where a plausible chained value usually already lives — e.g. `pm.environment.set("user_id", pm.response.json().id)` in a `test` script is the signal that `Get User`/`Update User`/`Delete User` need `{{process.user_id}}` in their URL.

### Mapping a Postman request to Voiden blocks

Each `item.request` (Postman v2.1) maps onto one section's blocks:

| Postman field | Voiden block | Notes |
|---|---|---|
| `request.method` + `request.url` | `request` (method + url) | `url` can be a string or `{raw, host, path, query, variable}` — use `.raw` either way. Convert `:id` segments to `{id}`. Skip this block entirely for a GraphQL body (see below) — the endpoint lives in `gqlurl` instead. |
| `request.auth` | `auth` | `auth.type` selects the sub-config array to read (`auth.basic`, `auth.bearer`, ...); each is an array of `{key, value}` pairs, not a flat object — e.g. `auth.type: "bearer"` → read `auth.bearer.find(p => p.key === "token").value`. Covers basic/bearer/apiKey/oauth1/oauth2/digest/ntlm/awsSignature/hawk; skip unrecognized types (e.g. `edgegrid`) rather than guessing a shape. |
| `request.header[]` (where `!disabled`) | `headers-table` | Row: `[key, value, description]` (`header.description` may be a string or `{content, type}` — use `.content` for the latter). |
| `request.url.variable[]` (or `:name` segments inferred from `request.url.raw` if `variable` is absent) | `path-table` | Row: `[key, value, description]`. |
| `request.url.query[]` (where `!disabled`) | `query-table` | Row: `[key, value, description]`. |
| `request.body` where `mode: "raw"` | `json_body` / `xml_body` | Language comes from `body.options.raw.language`, or sniff `body.raw` (`{`/`[` → json, `<` → xml/html) when absent. |
| `request.body` where `mode: "urlencoded"` | `url-table` | From `body.urlencoded[]` (where `!disabled`). |
| `request.body` where `mode: "formdata"` | `multipart-table` | From `body.formdata[]` (where `!disabled`); a `type: "file"` field's `src` path becomes a `fileLink` attachment if it still exists on disk, otherwise keep the path as plain text. |
| `request.body` where `mode: "graphql"` | `gqlquery` + `gqlvariables` | `body.graphql.query` → `gqlbody.body` (detect `query`/`mutation`/`subscription` from the text); `body.graphql.variables` (a JSON-encoded string) → a separate `gqlvariables` block. The `request` block is omitted — the URL goes in `gqlurl` instead. |
| `event[]` where `listen: "prerequest"` | `pre_script` | **Translate when every line is a recognized safe pattern, otherwise comment out in full.** See "Translating pm.* scripts" below. |
| `event[]` where `listen: "test"` | `post_script` | Same policy, applied to the test/assertion script instead. |

### Translating `pm.*` scripts into live `voiden.*` code

Postman scripts use the `pm.*` sandbox API; Voiden scripts use `voiden.*`/`vd.*` (see `voiden-scripting`'s skill for the full reference) — the two aren't source-compatible, so a blanket "just copy the script" isn't safe. But a real, useful subset of `pm.*` calls maps directly onto `voiden.*`, and translating those live (instead of leaving every script commented for manual review) is worth doing — **as long as it's all-or-nothing per script**: translate the whole thing only if *every* line resolves to a recognized pattern below; if even one line doesn't, leave the *entire* script commented exactly as before. Never emit a half-translated, half-commented script — that's harder to review than a fully-commented one.

**Safe to translate:**

| Postman | Voiden | Notes |
|---|---|---|
| `pm.environment`/`collectionVariables`/`globals`/`variables`.`get`/`set` | `voiden.variables.get`/`set` | Collapses Postman's 4 variable scopes into Voiden's one runtime-variable store — a real simplification, not a perfect equivalent, but the only R/W store `voiden.*` scripting exposes. |
| `pm.response.json()` / `.text()` | `voiden.response.body` | Method call → property (Voiden's body is already parsed if JSON). |
| `pm.response.code` | `voiden.response.status` | Postman's naming is inverted from what you'd guess — `code` is the number. |
| `pm.response.status` (the string, e.g. `"OK"`) | `voiden.response.statusText` | |
| `pm.response.responseTime` / `.responseSize` | `voiden.response.time` / `.size` | |
| `pm.response.headers.get(name)` | `voiden.response.headers[name]` | |
| `pm.request.headers.add(...)`, `.url`, `.method`, `.body.raw` | `voiden.request.headers.push(...)`, `.url`, `.method`, `.body` | |
| `console.log(...)` | `voiden.log(...)` | |
| `pm.test(name, function(){ ... })` wrapper | *(dropped — assertions become flat top-level `voiden.assert` calls; Voiden has no test-grouping wrapper)* | |
| `pm.expect(x).to.eql(y)` / `.equal(y)` | `voiden.assert(x, "==", y)` / `voiden.assert(x, "===", y)` | |
| `pm.expect(x).to.be.above/below/at.least/at.most(y)` | `voiden.assert(x, ">"/"<"/">="/"<=", y)` | Also `.greaterThan`/`.lessThan`/`.gte`/`.lte` spellings. |
| `pm.expect(x).to.include/contain(y)` | `voiden.assert(x, "contains", y)` | |
| `pm.expect(x).to.be.true/.ok` / `.to.be.false` | `voiden.assert(x, "truthy")` / `voiden.assert(x, "falsy")` | |
| `pm.response.to.have.status(n)` (Postman shorthand) | `voiden.assert(voiden.response.status, "==", n)` | |

**Never translate, always leave commented:** `pm.expect(x).to.match(regex)` (voiden.assert's exact handling of a RegExp value for `"matches"` isn't confirmed — guessing wrong here is worse than leaving it commented), `.to.have.property/lengthOf/be.a(...)`/other type-or-shape matchers (no `voiden.assert` equivalent exists), `pm.sendRequest(...)` (no outbound-fetch primitive in Voiden's scripting API), any control flow (`if`/`for`/`while`), custom helper functions, or anything else not in the table above.

A `pm.*` call nested *inside* an assertion's expression (e.g. `pm.expect(x).to.eql(pm.environment.get("y"))`) is fine — the variable/field substitutions apply anywhere in an expression, not just as a whole statement. But the reverse check matters too: if a captured expression still contains an untranslated `pm.*` call after substitution (something not in the table, e.g. `pm.response.headers.has(...)`), that specific line — and therefore the whole script — must fall back to commented, not ship with a leftover `pm.*` reference inside otherwise-live code.

### Placing a section's documentation

A heading meant to describe an upcoming section (e.g. `## Create User`) must go **after** that section's `request-separator`, never before — content before a separator belongs to the section that *precedes* it. Default to the separator's own `label` for naming the section; only add prose after it for something the label can't convey (auth requirements, expected status codes).
